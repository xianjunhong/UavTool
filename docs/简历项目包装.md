# UavTool 简历项目包装（遥感大模型工程师方向）

## 一、推荐项目名

**UAV-RS Workbench：面向遥感大模型的数据生产与无人机航测平台**

这个名字突出“无人机遥感 + 数据工程 + 工具链”。项目当前没有模型训练或推理模块，因此不建议直接命名为“遥感大模型平台”，否则面试时容易被追问穿透。

## 二、可直接粘贴到简历的版本

### UAV-RS Workbench：面向遥感大模型的数据生产与无人机航测平台

**项目介绍：** 面向农业与无人机遥感场景，独立设计并实现桌面端数据生产工具，打通“大幅面 GeoTIFF 导入—多尺度可视化—控制点几何校正—地块 ROI 管理与批量裁剪—DJI 航线任务生成”流程，为遥感大模型的样本预处理、空间对齐和外业数据采集提供统一工具链。

**技术栈：** Python、PySide6、GDAL/OGR、NumPy、pyproj/PROJ、QThread、GeoTIFF、Shapefile/GeoJSON/GPKG、DJI WPML/KML/KMZ、PyInstaller

- 设计六模块遥感数据工作台，将航线规划、影像金字塔、控制点配准、任意多边形裁剪、地块批处理和 Shapefile 汇总解耦为 UI、业务逻辑与地理计算三层；使用 QThread 执行配准、裁剪、合并和金字塔构建，避免大文件处理阻塞界面。
- 实现大幅面、多光谱 GeoTIFF 的多分辨率浏览：构建 4～64 倍共 5 级轻量 Overviews，按当前视窗动态读取影像窗口，并采用 2%～98% 分位拉伸、NoData 过滤和 RGB/MS 波段映射，兼顾磁盘占用、加载效率与遥感影像显示效果。
- 基于 NumPy 最小二乘实现不少于 3 对控制点的仿射几何校正，组合影像 GeoTransform 完成地理定位写回；输出训练 RMSE、最大误差、留一 RMSE，并通过矩阵秩、行列式和条件数识别共线点及病态变换。
- 基于 GDAL Warp/OGR 建立地块 ROI 数据生产链路，支持自相交多边形检测与修复、Alpha 掩膜裁剪、TILED/DEFLATE/BIGTIFF 输出，以及 Shapefile、GeoJSON、GPKG 跨坐标系加载和批量导出；支持多个小区 Shapefile 跨 CRS 合并，保留小区编号与整列编号规则，并消除跨文件列 ID 冲突。
- 将影像像素坐标经投影坐标转换为 WGS84 航点，按 DJI WPML 1.0.6 生成 template.kml 与 waylines.wpml，支持 M300/M3T 机型、飞行高度/速度、航向、云台俯仰与拍照动作配置；项目样例已批量处理 22 个 KMZ、共 2108 个航点，并通过 PyInstaller 交付 Windows 可执行版本。

## 五、60 秒面试介绍

这个项目本身不是为了“套一个大模型接口”，而是解决遥感模型落地前最耗工程时间的数据入口问题。无人机原始正射影像通常尺寸大、坐标系复杂，还需要几何校正和按地块生产样本。我用 GDAL、OGR、NumPy 和 PySide6 做了一套桌面工作台：前端采用金字塔和视窗级读取流畅浏览大图；中间用控制点最小二乘求仿射变换，并用 RMSE、留一误差和条件数做质量控制；下游将矢量地块跨 CRS 映射到影像并批量裁成 GeoTIFF/PNG，还能将多个小区 Shapefile 保留编号汇总成统一地块库；同时还能把影像上的目标点转换成 WGS84 航点，生成 DJI 可执行的 WPML/KMZ 任务。这个项目让我完整处理了栅格、矢量、坐标变换、数据质量和桌面工程交付问题，也构成了遥感大模型训练与推理前的数据底座。

## 六、面试高频追问与回答要点

### 1. 这和“遥感大模型”有什么关系？

不要回答“项目用了大模

型”。推荐回答：

> 当前版本聚焦模型上游的数据工程，包括多光谱显示、几何校正、ROI 样本生产、坐标一致性和数据采集闭环。它可以作为分割、检测、视觉语言模型训练或推理的统一数据入口；模型服务是下一阶段接入点。

### 2. 为什么要建金字塔？

全分辨率读取大幅面 GeoTIFF 会造成高 I/O 和内存开销。项目预构建 4、8、16、32、64 倍共 5 级轻量 Overviews；浏览时先显示低分辨率底图，再依据当前视窗和缩放比例读取局部窗口，从而避免每次缩放都加载整幅影像，并减少内部金字塔的磁盘占用。

### 3. 配准是怎么做的？

用户在源影像和目标影像上选择同名控制点，系统构造二维仿射变换的线性方程组，通过最小二乘求 6 个参数；再把像素域变换与源影像 GeoTransform 组合，写入目标影像副本。除了拟合 RMSE，还计算留一 RMSE，并用矩阵秩、行列式和条件数检测共线点或病态解。

### 4. 如何保证不同矢量数据能正确裁剪？

加载矢量图层后读取源 CRS；若与当前影像 CRS 不一致，则通过 OGR CoordinateTransformation 转换到目标 CRS，并统一 GDAL 3 的传统 GIS 轴顺序。裁剪前将像素多边形转换到地理坐标，再由 GDAL Warp 按 Cutline 输出。

### 5. 项目中最有工程价值的设计是什么？

可以从三点回答：

1. 大图不整图读取，而是“金字塔底图 + 当前视窗局部细节”。
2. 配准不只给结果，还暴露误差和数值稳定性指标。
3. 把地块从一次性手绘升级为可复用矢量库，支持跨影像、跨 CRS 批量生产样本和保留编号合并。

## 八、简历中可以使用的真实数字

以下数字已从当前代码或项目样例中核验：

- 6 个核心业务模块。
- 5 级轻量影像金字塔：4、8、16、32、64。
- 超过 1.2 亿像素且无金字塔的影像会被拦截，提示先构建 Overviews。
- 支持至少 3 对控制点；4 对及以上时计算留一 RMSE。
- 支持 3 种矢量输入：Shapefile、GeoJSON、GPKG；地块库保存为 Shapefile。
- 支持 GeoTIFF、PNG 两种裁剪输出。
- 支持 M300、M3T 两类 DJI 机型配置。
- 当前 input/output 样例包含 22 个 KMZ、2108 个航点。

建议另外补测并替换到简历中的数字：最大实测影像尺寸、单幅文件大小、批量地块数量、处理耗时、峰值内存，以及人工流程耗时降低比例。没有测量前不要编造。

## 九、当前边界与补强优先级

当前项目能证明较强的遥感数据工程能力，但还不能单独证明“大模型训练/微调/推理”能力。若用于应聘遥感大模型工程师，建议按以下顺序补强：

1. 增加遥感训练样本切片模块：固定窗口、Overlap、NoData 比例过滤、标签同步切片、JSONL/Parquet Manifest、按空间区域划分 train/val/test。
2. 接入一个真实模型闭环：例如 SegFormer/Swin-UNet 做地物分割，或 RemoteCLIP 做图文检索；保留 GeoTransform，将预测掩膜矢量化并写回 GeoJSON/GeoTIFF。
3. 增加基准测试脚本，记录影像尺寸、波段数、耗时、吞吐、峰值内存和精度指标，形成可复现的 benchmark 表。
4. 增加单元测试与 CI，覆盖仿射求解、CRS 转换、多边形修复、KMZ XML 结构和批量任务异常恢复。

如果时间只够做一项，优先完成“带地理参考的样本切片 + 一个分割模型推理 + 结果写回地图”，它能把当前的数据工程项目升级为完整的遥感模型工程闭环。

## 十、避免过度包装

- 不要写“支持亿级影像秒开”，除非有统一硬件上的实测数据。
- 不要写“配准精度提升 xx%”，除非有独立检查点或真实标注对比。
- 不要写“遥感大模型训练平台”，当前代码没有训练、微调、分布式训练或模型服务。
- 不要把 ROI 裁剪描述成“自动标注”；当前功能是人工绘制/加载矢量后的样本生产。
- 不要把两种无人机配置写成“兼容所有 DJI 机型”。
